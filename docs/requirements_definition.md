## 1. 背景と解決したいこと

転職を考えるきっかけは、日々の不満であることが多い。
不満から考え始めると、何を変えたいのかを整理しないまま、「転職する」という手段を先に決めてしまう可能性がある。

組織の業務改善で使われる「理想と現状の差を問題とし、原因から課題と手段を導く手順」は、
転職の悩みの整理にも役立つ可能性がある。
一方、この手順では、問題と課題、手段と理想など、近い概念を取り違えやすいと考えられる。
紙のワークシートなどでは、記入しながら取り違えに気づく仕組みがない。

そこで、本アプリでは、業務改善で使われる問題解決の手順とAIによる問い返しを組み合わせて  
転職の悩みの整理をサポートすることを目指す。

背景の根拠と仮説は [設計思想](concept.md) の1章・2章を参照。

## 2. 目的とゴール

### 2.1 目的

転職を考え始めた人が、記入しながら取り違えに気づき、
「何を変えたいのか」と「転職がその手段として適切か」を自分で判断できるようにする。

### 2.2 MVPのゴール

ユーザーが自分の転職の悩みについて、理想から手段までを順に考え、
AIの問い返しをきっかけに取り違えに気づいて自分で直せる。
最後に、自分で考えた問題の構造を図で確認できる。

## 3. 対象ユーザーとユースケース



### 3.1 対象ユーザー

今の仕事に不満やモヤモヤがあり、転職を考え始めたが、まだ具体的に動いていない20代から30代前半の社会人。

### 3.2 ユースケース


| 項目               | 内容                                                     |
| ---------------- | ------------------------------------------------------ |
| 誰が               | 転職を考え始めた20代から30代前半の社会人                                 |
| いつ・どんな状況で        | 求人を探したり、応募したりする前に、自分の考えを整理したいとき                        |
| 何に困っているか         | 「転職したい」「この職種に就きたい」など手段から考え始めていて、それで何が解決するのかを自分でも説明できない |
| ThinkStepsで何をするか | 理想から手段までを順に入力する。AIの問い返しを受けて、必要に応じて書き直す                 |
| 使い終わったとき         | 何を変えたいのかを言葉にでき、選ぼうとしている手段(転職を含む)が、それに対応しているかを自分で判断できる  |




## 4. ステップと用語の定義


| No  | ステップ  | 定義                             | 必須  |
| --- | ----- | ------------------------------ | --- |
| 1   | 理想    | 仕事や働き方を通じて実現したい状態              | ○   |
| 2   | 前提・制約 | 取り組むうえで変えられない、または今回は変えないと決めた条件 | 任意  |
| 3   | 現状    | 理想と同じ観点から見た、現在の状態              | ○   |
| 4   | 問題    | 理想と現状の差                        | ○   |
| 5   | 原因    | 問題を生み出している要素                   | ○   |
| 6   | 課題    | 問題を解くために取り組むべき方向性              | ○   |
| 7   | 手段    | 課題に取り組むための具体的な行動(転職を含む)        | ○   |


判定基準(OK例・NG例、混同しやすいペアの違い)は [思考フレームワーク](thinking_framework.md) で定める。

## 5. なぜAIを使うか・代替案との比較



### 5.1 AIを使う部分と使わない部分


| 機能                | AI   | 理由                     |
| ----------------- | ---- | ---------------------- |
| ステップの順序制御、入力の保持   | 使わない | 通常のプログラムで確実に実現できる      |
| 空欄・文字数のチェック       | 使わない | 単純なルールで判定できる           |
| 取り違え・ずれの判定        | 使う   | 自由記述の意味を読む必要がある        |
| 深刻な内容の検知          | 使う   | 表現が多様で、単語だけでは判定しきれない   |
| 問い返し文の生成          | 使う   | 入力内容に合わせて毎回変える必要がある    |
| 深刻な内容が検知されたときの案内文 | 使わない | 不正確な案内を避けるため、固定の文を表示する |
| 構造図の描画            | 使わない | 入力をそのまま図にするため          |




### 5.2 AIが必要な理由

記入内容について、各項目を取り違えていないか、前後の整合を判定するには、語尾や単語などのルールでは判定できず、AIが必要である。また、随時、記入内容に対して問い返しする仕組みを運用するには、AIが必要である。

### 5.3 代替案との比較


| 観点               | 紙のワークシート | ルールによる判定   | 汎用の対話型AI            | ThinkSteps      |
| ---------------- | -------- | ---------- | ------------------- | --------------- |
| 記入中に取り違えに気づける    | ×        | △ 定型的なものだけ | ○                   | ○               |
| 答えや助言を出さないことの確実さ | ○        | ○          | △ 指示しないと助言や答えを出しやすい | ○ 設計で制限し、テストで確認 |
| ステップの順序と前後の整合    | △        | △          | △ 毎回の指示が必要          | ○               |
| 判定の柔軟さ           | −        | ×          | ○                   | ○               |
| 費用               | なし       | なし         | 利用料                 | API利用料          |
| 誤判定のリスク          | −        | 低い         | あり                  | あり(却下できる設計で対応)  |


判定精度と「答えや助言を出さないことの確実さ」は仮説であり、
9章の評価で、ルールによる判定と比べて確かめる。

## 6. AIの役割



### 6.1 AIがすること

- 各ステップの入力について、次の観点で判定する
  - 項目の取り違え(特に、問題と課題の混同、手段の入り込み)
  - 前後の項目との整合(例: 理想と現状が同じ観点で書かれているか)
  - 前提・制約との整合
  - 意味が複数に解釈できる表現になっていないか
  - 深刻な内容が含まれていないか
- 判定にもとづき、気づくための問いを1つ返す
- 適切に書けている点があれば、先に伝える
- 問題がなければ問い返さない



### 6.2 AIがしないこと

- 理想、問題、原因、課題、手段を代わりに考える、または候補を示す
- 転職すべきかどうかを判断する
- 職種、企業、資格などを勧める、または否定する
- 正解を断定する
- ユーザーの意図を推測して入力を補完する
- 深刻な内容に対して、自ら案内文を作る



### 6.3 問いの線引き


| 区分              | 例                                         |
| --------------- | ----------------------------------------- |
| 許容する問い(気づきを促す)  | 「この文は、理想と現状のどの差を表していますか？」                 |
| 許容する問い(観点の確認)   | 「理想では仕事での手応えについて書いていますが、現状は何について書いていますか？」 |
| 許容する問い(手段から目的へ) | 「転職した先で、どんな状態になっていたいですか？」                 |
| 禁止する問い(答えの提示)   | 「問題は『手応えを感じられていないこと』ではないでしょうか」            |
| 禁止する問い(誘導)      | 「これは課題ではないですか？」                           |
| 禁止する問い(原因の示唆)   | 「裁量のない職場にいることが原因ではありませんか？」                |
| 禁止する問い(キャリアの助言) | 「品質管理の経験は、生産管理の仕事に活かせそうです」                |




### 6.4 ユーザーの判断の優先

AIの指摘は仮説として扱う。ユーザーは指摘を受けて修正するか、そのまま進むかを選べる。

## 7. 機能要件



### 7.1 MVP


| ID   | 機能           | 内容                                                                            |
| ---- | ------------ | ----------------------------------------------------------------------------- |
| F-01 | 悩みの自由記述      | 最初に、今考えていることを自由に書ける(任意)。AIは判定しない。試用時に、悩みが手段から始まっているか(設計思想 仮説1)を確かめるために使う      |
| F-02 | ステップ入力       | 理想から手段までの7ステップを順に入力できる。前提・制約は任意                                               |
| F-03 | 入力の補助        | 各ステップの入力欄に、そのステップの説明と記入例(架空の人物)を表示する                                          |
| F-04 | AIによる判定と問い返し | 入力ごとにAIが判定し、必要な場合は問いを1つ返す。良い点があれば先に伝える                                        |
| F-05 | 修正またはそのまま進む  | 問い返しを受けたあと、修正して再判定するか、そのまま次に進むかを選べる                                           |
| F-06 | 前のステップへの戻り   | 前のステップに戻って入力を編集できる。編集したステップは再判定する                                             |
| F-07 | 構造図の表示       | 全ステップの入力を、理想から手段までのつながりとして図で表示する                                              |
| F-08 | 利用上の注意の表示    | 入力が外部AIサービスに送信されること、職場名・人名など個人や組織が特定できる情報を入力しないことを表示する                        |
| F-09 | 深刻な内容への対応    | AIが深刻な内容を検知した場合、そのステップの判定と問い返しを行わず、固定の案内文と相談先(8.8)を表示する。ユーザーは入力を見直して続けることができる |
| F-10 | 相談先への常時リンク   | 画面の下部に、相談先の一覧へのリンクを常に表示する(AIが深刻な内容を見逃した場合に備えるため)                              |


MVPでは、各ステップの入力は1件ずつとする(1件の中に箇条書きで複数書くことは妨げない)。 原因・課題・手段を複数登録して対応関係を結ぶ機能はv2で扱う。

### 7.2 v2以降の候補

- 原因・課題・手段の複数登録と、対応関係の表示
- 「その手段で理想に近づくか」を最後に確かめる振り返り(ロジックモデルの考え方の応用)
- 整理した結果の出力(PDFなど)
- 履歴の蓄積と、入力傾向の振り返り



## 8. 非機能要件



### 8.1 データの取り扱い

- 入力内容はサーバーやデータベースに保存せず、利用中の画面の中だけで保持する。
- 入力内容をログに記録しない。
- 入力内容は判定のために外部のAIサービス(OpenAI API)に送信される。このことを画面に表示する。
- 外部AIサービスでの入力データの扱いは、利用規約を確認してREADMEに記載する。



### 8.2 セキュリティ

- APIキーは環境変数またはデプロイ先の秘密情報管理機能で管理し、リポジトリに含めない。
- ユーザーの入力とAIへの指示を明確に区切り、入力に含まれる指示文に従わないようにする。
- AIの出力は決められた形式(JSON)に固定し、形式が正しいか確認してから表示する。
- 1回の入力の文字数に上限を設ける(例: 300字)。



### 8.3 費用

- 1回の判定で使うトークン数(AIが文章を処理する単位)に上限を設ける。
- APIの利用額に月の上限を設定する。
- 1回の整理(7ステップ)にかかる費用を評価時に計測し、READMEに記載する。



### 8.4 応答時間

- 1回の判定は10秒以内を目標とする。
- 判定中は待機中であることを画面に表示する。



### 8.5 エラー時の動作

- AIサービスの障害や時間切れの場合は、分かりやすいメッセージと再試行ボタンを表示する。
- 判定できない場合も、次のステップに進める。
- 判定できない場合も、相談先へのリンク(F-10)は表示されたままにする。



### 8.6 判定の安定性

- 同じ入力に対する判定のばらつきを減らす設定にする(出力のランダムさを下げる)。
- 使用するモデルのバージョンを固定し、変更時は評価をやり直す。



### 8.7 使いやすさ・アクセシビリティ

- 問い返しは、否定ではなく別の見方を提案する言葉づかいにする。
- やわらかく親しみやすいデザインにする。
- 文字と背景のコントラストを十分に確保する。
- 色だけで情報を伝えない(アイコンや文字を併用する)。



### 8.8 相談先の表示

深刻な内容が検知されたとき(F-09)と、画面下部のリンク先(F-10)では、次の公的な窓口を案内する。
電話番号や受付時間は変わることがあるため、アプリには各窓口の公式ページへのリンクを中心に掲載し、
公開前と、その後も定期的に、公式ページで内容を確認する。


| 窓口                        | 内容                                                     | 公式ページ                                                                                                        |
| ------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| まもろうよ こころ(厚生労働省)          | 電話・SNSなどの相談窓口の案内。こころの健康相談統一ダイヤル、よりそいホットライン、いのちの電話などを掲載 | [https://www.mhlw.go.jp/mamorouyokokoro/soudan/tel](https://www.mhlw.go.jp/mamorouyokokoro/soudan/tel)       |
| こころの耳(厚生労働省)              | 働く人のメンタルヘルスに関する情報と、電話・SNS・メールによる「働く人のこころの耳相談」          | [https://kokoro.mhlw.go.jp/](https://kokoro.mhlw.go.jp/)                                                     |
| あかるい職場応援団 相談窓口のご案内(厚生労働省) | ハラスメントなど職場の問題の相談先の案内(総合労働相談コーナーなど)                     | [https://www.no-harassment.mhlw.go.jp/inquiry-counter](https://www.no-harassment.mhlw.go.jp/inquiry-counter) |


案内文の案(固定の文):

> 入力された内容から、心身の不調やつらい状況にあるように見受けられました。
> このステップの判定は行いません。ひとりで抱えず、下の相談窓口を利用することも考えてみてください。
> 命に関わる緊急の場合は、119番に連絡してください。

(2026年11月4日に各公式ページを確認。内容は変わる可能性がある)

### 8.9 利用環境

- PCとスマートフォンのブラウザで利用できる。



## 9. 成功基準と評価方法



### 9.1 MVPの完成条件

- 7ステップを順に入力できる。
- 各ステップでAIの判定と問い返しを受けられる。
- 深刻な内容が検知されたときに、案内文と相談先が表示される。
- 最後に、入力内容を構造図として確認できる。
- 公開URLで、第三者が利用できる。



### 9.2 AIの判定品質


| 指標           | 内容                             | 目標(暫定)    |
| ------------ | ------------------------------ | --------- |
| 混同の検出率       | 取り違えを含む入力のうち、正しく指摘できた割合        | 80%以上     |
| 過剰指摘率        | 適切な入力のうち、誤って指摘してしまった割合         | 20%以下     |
| 問題と課題の混同の検出率 | 重点項目                           | 80%以上     |
| 手段の入り込みの検出率  | 重点項目。転職や職種名を理想・問題・課題に書いた入力の検出率 | 80%以上     |
| 深刻な内容の検出率    | 深刻な内容を含む入力のうち、検知できた割合          | 100%      |
| 深刻な内容の過剰検知   | 日常的な不満や疲れを、深刻な内容と判定した件数        | 記録して傾向を見る |
| 禁止事項の遵守      | 問いに答え・候補・キャリアの助言が含まれた回数        | 0回        |
| 問い返しルールの遵守   | 問いが1つ、否定的な表現がない、などのルールを守った割合   | 90%以上     |


評価方法:

- [テストデータの仕様](testcases_spec.md) にもとづき、架空のテストデータ(data/testcases.csv)を作成する。
- テストデータは、プロンプト調整用と最終検証用に分け、最終検証用は最後に1回だけ使う。
- ルールによる簡易判定と比較し、AIを使う効果を確認する。
- 結果は docs/evaluation.md に記録する。



### 9.3 利用者による試用


| 指標          | 内容                                        | 目標(暫定)         |
| ----------- | ----------------------------------------- | -------------- |
| 手段から考え始める傾向 | 悩みの自由記述(F-01)が、手段(転職する、職種を変えるなど)から始まっているか | 記録して傾向を見る(仮説1) |
| 整理できた実感     | 「何を変えたいのかを整理できた」を5段階で評価                   | 平均4以上          |
| 手が止まったステップ  | どのステップで止まったか、業務とは異なる難しさがあったか              | 記録して傾向を見る(仮説3) |
| 取り違えの傾向     | どのステップで、どの取り違えが起きたか                       | 記録して傾向を見る(仮説4) |
| 書き直した割合     | AIの問い返しのあと、自分で入力を直した割合                    | 記録して傾向を見る      |
| 心理的な負担      | 「責められている感じがしなかった」を5段階で評価                  | 平均4以上          |


評価方法:

- 3〜5人に、自分の転職の悩みで試用してもらい、結果を docs/user_test.md に記録する。
- 人数が少ないため、効果の証明ではなく傾向の確認とする。
- 試用者の入力内容は記録せず、指標に必要な情報だけを記録する。



### 9.4 非機能面

- 1回の判定の応答時間: 10秒以内
- 1回の整理(7ステップ)の費用: 計測して記録する

目標に届かなかった場合は、結果・原因・対策を限界として記録する。

## 10. スコープ外

- 転職すべきかどうかの判断、職種や企業の提案、求人情報の提供
- 心の不調への対応(相談先の案内のみ行う)
- ログイン、利用者の管理
- データベースへの保存、整理の履歴
- 答えや解決策を提示する機能
