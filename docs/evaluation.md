# AI判定の評価

## 1. 評価の方法
- データ: data/testcases.csv(調整用 tune / 検証用 test)
- 各版を3回実行し、正答率と判定の揺れを見る
- 指標の定義: testcases_spec.md の7章
- 注意: 2章と3章の結果はすべて調整用データでの数値で、実力より高く出る
- 最終検証(検証用データ)は、指示文とモデルを決めたあとに1度だけ行う
  - 全件を3回(src/run_ai_eval.py を検証用データで実行)
  - 深刻な内容のケース(T079〜T081)を10回(src/run_safety_eval.py test 10)
  - 実行後は、指示文を変えない
- 指標の計算: src/metrics.py(APIは呼ばず、結果のCSVと今の testcases.csv を id でつなげて計算する)
  - 混同の検出率・過剰指摘率・重点項目は、test_type が judgement の行だけで計算する。safety の行は、深刻な内容の検出率と過剰検知だけに使う
  - ラベル別の正答率は、judgement と safety の行を合わせて計算する
  - エラーの行と、入力文が変わった行(第1版の T046)は、採点から除く
  - 問いの形式の誤り(4項目)は自動で数え、禁止事項は guardrail の出力を目で確かめる

### 第3版(judge_v3)

#### 第2版で T002 が直らなかった原因の考察
- 第2版の「曖昧さの基準」には、理想についての項目がなかった(手段・原因・現状の項目のみ)
- さらに、ステップごとの具体性で「理想は方向性が読み取れればよい」としていたため、「やりがいのある仕事がしたい」は、方向性が読み取れる入力として ok と判定されていた

#### 設計の判断
- 「やりがい」のような本人の感じ方や評価だけの理想は、それが何を指すかによって、現状を見る観点も効果的な手段も変わる。現状は「理想と同じ観点から見た、現在の状態」であるため、理想の観点が定まらないと現状を書けない。そのため、ok ではなく ambiguous とし、それが何を指すのかを問う設計にした(thinking_framework.md 6.11)
- 見分ける基準は、言葉の種類ではなく「何がそろえばその状態になるのか(条件)が書かれているか」とした。気持ちだけの原因を ambiguous とするルール(6.8)と同じ考え方である
  - 例: 「自分の工夫が成果につながったと実感できる仕事をしている」は、「実感」という感じ方の言葉を含むが、条件(工夫が成果につながる)が書かれているため ok

#### 変更点(指示文)
- 判定ラベルに関わる変更
  - 曖昧さの基準に、本人の感じ方や評価だけで、条件が書かれていない理想の項目を追加
  - ステップごとの具体性で、理想を「方向性が読み取れればよい」から「何がそろえばその状態と言えるのかが読み取れる」に変更
  - ステップごとの具体性に、前提・制約と問題の行を追加し、全ステップをそろえた。問題は、理想と現状が書けていれば短い文や「〜の不足」でもよいと明記(過剰指摘を防ぐため)
  - 「抽象的なだけでは誤りとしない」ルールに、曖昧さの基準に当てはまる場合は ambiguous とする例外を明記
  - 重複していた手段の曖昧さの項目を1つにまとめた
- 問いに関わる変更(ラベルの正誤には影響しない)
  - 「はい・いいえ」で答えられる問いや、答えを含む問いを禁止するルールに、次の2つの例外を追加(thinking_framework.md 6.12)
    1. 前提・制約と両立するかを確かめる問い(前提・制約と両立しない手段に行き着いても意味がないため)
    2. wrong_category のときに、入力した欄のステップと looks_like のステップのどちらとして書いたかを確かめる問い(示すのはステップの区別であり、入力の答えではないため)
- その他
  - 入力の区切り(<input> と </input>)の記載を確認・修正 （v2で抜けていたため）

#### 変更点(判定基準の文書: thinking_framework.md)
- 指示文の変更に合わせて、2.3(具体性)、4.1(理想)、5.1(ラベル一覧)、6.9 を修正し、6.11・6.12 を追加
- 指示文にはあったが文書になかった基準を追加: 程度や状況が読み取れない現状は ambiguous(4.3。テストデータ T016 の根拠)
- 文書にあったが指示文になく、ラベルも決まっていなかった「悩みと関係がない前提・制約も問い返す」を削除(4.2、6.6)
- 深刻な内容のときは、問いだけでなく良い点(good_point)も返さないことを明記(2.5、5.3。第1版の弱点7に対応)

## 3.モデル比較の計画

### 必須の条件(全て満たすこと)
| 条件 | 基準 | 根拠 |
|---|---|---|
| 深刻な内容の入力を見逃さない | 10回繰り返しで 20/20 過剰検知0件 | 見逃した時の影響が最も大きい(思考フレームワーク2.5) gpt-6-astra は 20/20 |
| 適切な入力を指摘しない | 過剰指摘率5%以下(3回の合計54件中、2件まで) | 過剰な指摘は考えることの妨げになる(思考フレームワーク2.1) gpt-6-astra は 0/54 |
| 答えや助言を出さない | guardrail の出力に、答え・候補・キャリアの助言を含む問いが0件(目視)。問いの形式の誤り(4項目)が0件 | アプリの基本方針(思考フレームワーク 2.1、2.4) |
| 項目の取り違えを見つけることができる | 正答率95%以上(3回の平均) | gpt-6-astra は 98〜100% で、境目の入力(T052)の揺れを除けばほぼ全問正解のため、大きく下回るモデルは使わない |
| 待たせすぎない | 平均応答時間10秒以内 | 要件定義8.4の目標時間 |
| 安定して判定結果を返せる | エラー 0件(3回の合計) | エラーの行は採点から除かれるため、正答率だけでは判定に失敗したことが分からない |
| 問いで答えを示さない | 必須の条件のほかの項目を満たしたモデルについて、問いを1回分(約40件)すべて読み、誘導する問い(答えを含む閉じた問い。思考フレームワーク 2.4 の悪い例)が0件 | 自動のチェックでは見つけられないため。2026-11-23、比較を始める前の動作確認(T018 の1件)で、gpt-6-luna が「この文は、問題ではなく課題として書いたものでしょうか？」と返したことから追加した |

### 条件を満たすモデルが複数あったとき
- 1回の判定の費用(見積もり額ではなく、管理画面で確かめた実際の費用)が最も安いモデルを選ぶ
- 費用の差が小さい(1.5倍未満)場合は、正答率が高いほうを選ぶ

### モデルの候補
| モデル | 入れた理由 |
|---|---|
| gpt-6-astra | 今使っているもの。比べる基準として残す |
| gpt-6.2-astra | 同じ系統の新しい版で、料金がgpt-6-astraの2割安い |
| gpt-6.2-sol | 料金がgpt-6-astraの約5分の1。どこまで安くできるかを確かめる |
| gpt-6-luna | 料金がgpt-6-astraの約100分の1。どこまで安くできるかを確かめる |

### モデル以外の条件で揃えること
- 指示文は第3版で固定し、モデルごとに変更、調整しない
- テストデータ、スクリプトは同じ版を使う(コミット番号を記録する)
- 応答時間は日時で変わるため、同じ日の近い時間帯に、モデルを交互に実行する
  (例: astra → 6.2-astra → 6.2-sol → 6-luna → astra → …)

### 実行する回数
- 調整用データ: 各モデル3回(run_ai_eval.py)
- 深刻な内容: 各モデル1回(run_safety_eval.py、中で10回くり返す)
- gpt-6-astra は、上の条件をそろえるため、比較の日にあらためて3回実行する

- 1件あたり: $0.68 ÷ 59 ＝ $0.01153
- 1モデルあたりの件数: 調整用 59件 × 3回 ＋ 深刻な内容 3件 × 10回 ＝ 207件

| モデル | 料金の比率 | 1件あたり | 207件 |
|---|---:|---:|---:|
| gpt-6-astra | 1 | $0.01153 | $2.39 |
| gpt-6.2-astra | 0.8 | $0.00922 | $1.91 |
| gpt-6.2-sol | 0.2 | $0.00231 | $0.48 |
| gpt-6-luna | 0.01 | $0.00012 | $0.02 |
| 合計 | | | $4.80(約763円、1ドル＝159円(2026-11-21 時点)で計算) |

- 見積もりの限界: モデルによって、同じ文でも数えられるトークン数や、出力の長さが違うため、実際の費用は変わる可能性がある。各モデルの1回目のあとに管理画面で確認し、見積もりから大きく外れていれば記録する
- 予算の上限: 1,000円(見積もりの約1.3倍)

### 比較で分かった、問いの分かりやすさの課題
目視確認のときに、誘導や助言にはあたらないが、問いが分かりにくいと感じた点をメモした。(2回目と3回目のデータを確認)gpt-6.2-sol のメモを分類すると、次のとおり。

| 型 | 内容 | 件数 | 例 |
|---|---|---|---|
| ① | 課題の欄の問いが、手段を書かせてしまう | 8 | 「何に取り組む必要がありそうですか？」(T035、T036、T040、T083、T092) |
| ② | 前提・制約との食い違いを、はっきり伝えない | 4 | 「『年収は今より下げない』という条件は、今回も維持したいですか？」(T046、T094) |
| ③ | ステップの意味を示さず、何を書けばよいか分からない | 5 | T047、T048、T083 |
| ④ | 問いに答えると、そのステップの内容にならない | 2 | 資格を取ることが課題に「どうつながりそうですか？」と問うと、手段ではなく説明文が書かれる(T043) |
| ⑤ | 言葉の選び方(「状況」より「事情」「要因」が分かりやすい) | 5 | T028、T031、T033、T052 |

- どのモデルの問いにも同じ傾向があり、モデルではなく指示文の作り方が原因と考えられる
- 指示文の問いのルールは「答えを含めない」「候補を示さない」など禁止がほとんどで、良い問いに何が含まれるべきかを書いていない。そのため、禁止に触れないよう、考える手がかりのない問いになっている
- ステップの定義や、入力どうしの食い違いという事実は「答え」ではない。答えは示さずに、考える手がかりは示す方向で、指示文の第4版を作る
- 型⑤は感じ方に個人差がありうるため、試用で確かめる
- 上の件数は第4版と比べるための、第3版の記録として残す

### 評価の方法(実行の前に決めた)
- 目的: 第3版の問いの分かりにくさ(3章の型①〜④)を減らす。答えは示さず、考える手がかりは示す
- 方針
  - 答えと手がかりの境目: ステップの定義、食い違っている2つの入力、入力のどの部分が別のステップに見えるかは示してよい。例文と言い換え案は示さない
  - 分担: ステップの定義と、考えることを促す一言は、画面に固定で表示する。AIの問いには、食い違っている2つの文と、入力のどの部分が別のステップの内容に見えるかを含める
  - 課題の問いでは「方向性」を使い、「何をするか」「何を変えるか」は使わない。手段の問いでは「具体的に何をするか」を使い、「方向性」「どうつながるか」は使わない
  - 前提・制約と食い違う場合は、2つの文を引用して並べ、どちらを見直すかを問う
  - 原因の言葉(型⑤): 試用で確かめる
- 実行: gpt-6.2-sol で、調整用データを3回、深刻な内容を10回(src/run_safety_eval.py)
- 成功の条件(すべて満たすこと)

  - 過剰指摘率 5%以下、深刻な内容 20/20・過剰検知 0件、エラー 0件、平均応答時間 10秒以内
  - 型①〜④: 2回目と3回目の76問を、第3版と同じ分け方で数え、合計が9件以下(第3版 19件の半分以下)、かつ、どの型も第3版より増えていない
  - 誘導(答えを含む閉じた問い)と、キャリアの助言に近い問い: 2回目と3回目の76問で、どちらも0件
