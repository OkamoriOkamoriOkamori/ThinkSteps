# ThinkSteps 思考フレームワーク

> 本書は、AIが各ステップの入力を判定し、問いを返すときの基準(ルーブリック)を定める。
> プロンプトとテストデータは本書をもとに作成する。
> 「なぜ作るのか」は [設計思想](concept.md)、「何をどこまで作るか」は [要件定義](requirements_definition.md)、
> 例に使う人物は [架空の人物と記入例](../data/cases.md) を参照する。

## 1. 本書で使う例

本書の例は、[架空の人物と記入例](../data/cases.md) の3人(P01〜P03)から取る。
各ステップのOK例は、主にP01(Aさん)の記入例を使う。

> **P01 Aさん**(29歳、食品メーカーの品質管理、7年目)
> 毎日の仕事はこなせているが、やりがいを感じない。転職したほうがいいのか迷っているが、何がしたいのかは分からない。


| ステップ  | 適切な記入例(P01)                              |
| ----- | ---------------------------------------- |
| 理想    | 自分の工夫が成果につながったと実感できる仕事をしている              |
| 前提・制約 | 年収は今より下げない／今の住まいから通える範囲で働く               |
| 現状    | 担当業務の多くは決まった検査手順の繰り返しで、自分で工夫できる場面がほとんどない |
| 問題    | 仕事の中で工夫して成果を出す場面がなく、手応えを感じられていない         |
| 原因    | 検査の手順が細かく決められていて、進め方を任される仕事がない           |
| 課題    | 自分の工夫が成果に反映される仕事の範囲を広げる                  |
| 手段    | 検査手順の見直しを任せてもらえるよう、上司に相談する               |

## 2. 共通ルール



### 2.1 基本の考え方

- AIは、入力が「そのステップの役割を果たしているか」を判定する。文章の上手さや、考えの良し悪しは判定しない。
- 入力内容に不備がなければ問い返さない。不備があるか迷う場合も問い返さない(過剰な指摘は、考えることの妨げになるため)。
- AIはユーザーの意図を推測して補完しない。意図が読み取れない場合は、補完せずに問いで確認する。
- AIはキャリアの助言をしない。転職すべきかどうか、どの職種や企業が向いているかは、判定にも問いにも含めない。
- 深刻な内容が含まれる場合は、通常の判定より安全への対応を優先する(2.5)。



### 2.2 「観点」の定義

**本アプリでの「観点」とは、その入力が「何について」述べているかである。**

- 例: 「仕事での手応え」「給与」「家族と過ごす時間」「仕事の内容」
- 理想と現状は、同じ観点で書かれている必要がある。観点が違うと、差(問題)を定義できない。
- 判定方法: 理想と現状のそれぞれから「何について述べているか」を取り出し、同じ対象・同じ尺度で比べられるかを確認する。


| 理想                          | 現状                | 判定                   |
| --------------------------- | ----------------- | -------------------- |
| 自分の工夫が成果につながったと実感できる仕事をしている | 自分で工夫できる場面がほとんどない | 同じ観点(仕事での工夫と手応え)     |
| 自分の工夫が成果につながったと実感できる仕事をしている | 給料が低い             | 観点がずれている(仕事での手応えと給与) |




### 2.3 「具体性」の定義

**本アプリでの「具体性」とは、その入力から、対象と状態(または行動)を一つに特定できるかである。**

- 抽象的であること自体は誤りとしない。理想や課題は、ある程度抽象的でよい。
- 判定するのは「意味が複数に解釈でき、次のステップを考えられない」場合だけとする。
- 判定方法: 次の2点が読み取れるかを確認する。
  1. 対象: 何について(仕事の内容、働き方、収入など)
  2. 状態・行動: どうなっているか、何をするか


| 入力                          | 判定          | 理由                                 |
| --------------------------- | ----------- | ---------------------------------- |
| やりがいのある仕事がしたい               | 意味が複数に解釈できる | 何があれば「やりがい」なのか(状態)が特定できない          |
| 自分の工夫が成果につながったと実感できる仕事をしている | 適切          | 対象(仕事)と状態(工夫が成果につながったと実感できる)が特定できる |


ステップごとに求める具体性の程度は異なる。手段は「何をするか」まで読み取れる必要があるが、理想と課題は方向性が読み取れればよい。

### 2.4 問い返しのルール


| ルール         | 内容                                              |
| ----------- | ----------------------------------------------- |
| 1回に1つ       | 問いは1回につき1つまでとする。複数の指摘がある場合は、優先順位(5.2)の高いものを1つ選ぶ |
| 良い点を先に      | 適切に書けている点があれば、問いの前に短く伝える                        |
| 根拠を示す       | ユーザーの入力のどの部分について問うのかを示す                         |
| オープンな問い     | 「はい・いいえ」で答えられる問いや、答えを含む問いにしない                   |
| 答えを出さない     | 正しい記入例、候補、言い換え案を示さない                            |
| 原因や方向を示唆しない | 「〜が原因ではありませんか」「〜を目指してはどうですか」のように、特定の原因や方向を示さない  |
| キャリアの助言をしない | 転職の是非、職種、企業、資格などを勧めたり否定したりしない                   |
| 否定しない       | 「間違っています」「ずれています」ではなく、別の見方を提案する言葉づかいにする         |
| やさしい言葉      | 専門用語を避け、短い文にする                                  |


**問いの例**


| 区分           | 例                                           |
| ------------ | ------------------------------------------- |
| 良い例          | 「仕事での手応えに注目できていますね。この文は、理想と現状のどの差を表していますか？」 |
| 良い例          | 「理想では仕事での手応えについて書いていますが、現状は何について書いていますか？」   |
| 悪い例(答えの提示)   | 「問題は『手応えを感じられていないこと』ではないでしょうか」              |
| 悪い例(誘導)      | 「これは課題ではないですか？」                             |
| 悪い例(原因の示唆)   | 「裁量のない職場にいることが原因ではありませんか？」                  |
| 悪い例(キャリアの助言) | 「品質管理の経験は、生産管理の仕事に活かせそうです」                  |
| 悪い例(否定)      | 「理想と現状がずれています。書き直してください」                    |




### 2.5 深刻な内容への対応

入力に次のような内容が含まれる場合は、通常の判定を行わず、ラベル `safety_concern` を返す。

- 心身の不調が続いていることを示す内容(眠れない、食事がとれない、体調を崩しているなど)
- 自分を傷つけたい、消えたいといった気持ちを示す内容
- ハラスメントや暴力など、職場で深刻な被害を受けていることを示す内容

このとき、AIは問いを生成しない。アプリが、あらかじめ用意した固定の文で相談先を案内する。
相談先は要件定義で定め、公的な窓口を一次情報で確認したうえで掲載する。

**判定の注意**

- 「仕事がつらい」「疲れている」など、日常的な不満や疲れだけでは `safety_concern` としない。
- 迷う場合は `safety_concern` とする(見逃した場合の影響が大きいため、2.1の「迷う場合は問い返さない」の例外とする)。

## 3. 混同しやすいペアの対比表


| ペア       | 見分け方                                            | 混同した例                   | 本来の位置づけ         |
| -------- | ----------------------------------------------- | ----------------------- | --------------- |
| 理想と手段    | 理想は「実現したい状態」、手段は「そのための行動」                       | 理想に「転職したい」「Webデザイナーになる」 | 手段              |
| 理想と前提・制約 | 理想は「目指すもの」、前提・制約は「目指すうえで変えない条件」                 | 理想に「年収を下げずに働く」          | 前提・制約           |
| 前提・制約と現状 | 前提・制約は「今回は変えないと決めた条件」、現状は「理想と比べるための今の状態」        | 現状に「子どもが小さい」            | 前提・制約           |
| 現状と問題    | 現状は「今の状態」、問題は「理想との差」                            | 問題に「決まった検査手順の繰り返しが多い」   | 現状              |
| 問題と原因    | 問題は「理想との差」、原因は「その差を生む要素」                        | 問題に「デザインのスキルが足りない」      | 原因              |
| 問題と課題    | 問題は「理想と現状の差」、課題は「その差を解くために取り組む方向性」。語尾だけでは判断しない。 | 問題に「仕事の手応えを増やす」         | 課題              |
| 問題と手段    | 問題は「理想との差」、手段は「具体的な行動」                          | 問題に「転職できていない」           | 手段を前提にした問題      |
| 原因と気持ち   | 原因は「差を生む要素(状況や事実)」、気持ちは「その結果として感じていること」         | 原因に「やる気が出ない」            | 原因を生んでいる状況を確認する |
| 原因と課題    | 原因は「差を生む要素」、課題は「それを踏まえて取り組む方向性」                 | 原因に「もっと裁量のある仕事をする必要がある」 | 課題              |
| 課題と手段    | 課題は「何に取り組むか」、手段は「どのように取り組むか」                    | 課題に「土日休みの会社に転職する」       | 手段              |
| 前提・制約と原因 | 前提・制約は「変えないと決めた条件」、原因は「差を生む要素」                  | 原因に「子どもがいるから」           | 前提・制約           |


**重点項目**

- 問題と課題の混同を最も重点的に判定する。
- 転職や職種名を、理想・問題・課題に書く混同(手段の入り込み)を、転職版の重点項目として判定する。

## 4. ステップ別の判定基準

各ステップのNG例には、判定ラベル(5章)を付ける。テストデータは、これらの例をもとに作成する。
「人物」列は、文脈として使う人物の記入例を示す。

### 4.1 理想

**定義**: 仕事や働き方を通じて実現したい状態

**役割**: 現状と比べて問題を定める基準になる。最初に決めることで、不満や手段(転職など)から考え始めることを防ぐ。

**確認ポイント**

- 実現したい「状態」として書かれているか
- 意味が複数に解釈できないか
- 転職、職種名、資格など、手段になっていないか

**判定の注意**

- 理想がはっきり決まっていなくてもよい。仮の理想でも受け入れる。
- 職種名(「エンジニアになる」など)が書かれた場合は、その職種で実現したい状態を問う。職種を否定したり、別の職種を示したりしない。
- 数値目標がなくても受け入れる。


| 区分  | 人物  | 入力                              | ラベル                   |
| --- | --- | ------------------------------- | --------------------- |
| OK  | P01 | 自分の工夫が成果につながったと実感できる仕事をしている     | ok                    |
| OK  | P02 | 平日の夕方と週末に、子どもと過ごす時間を確保しながら働いている | ok                    |
| NG  | P01 | やりがいのある仕事がしたい                   | ambiguous             |
| NG  | P01 | 転職したい                           | wrong_category(手段)    |
| NG  | P03 | Webデザイナーになる                     | wrong_category(手段)    |
| NG  | P01 | 年収を下げずに働く                       | wrong_category(前提・制約) |


**問い返し例**

- 「仕事のどんな場面で、どんな状態になっていたら『やりがいがある』と感じられそうですか？」
- 「転職した先で、どんな状態になっていたいですか？」
- 「Webデザイナーとして働くことで、どんな状態を実現したいですか？」



### 4.2 前提・制約(任意)

**定義**: 取り組むうえで変えられない、または今回は変えないと決めた条件

**役割**: 変えられない、または変えたくない条件(家庭、住む場所、収入など)を、現状や問題から切り分ける。後のステップで、条件に反する課題や手段に気づけるようにする。

**確認ポイント**

- 本当に変えられない(または今回は変えない)条件か
- 今回の悩みに関係する条件か

**判定の注意**

- 空欄でもよい。
- 本人の希望による条件(「年収は今より下げない」など)も、今回は変えないと決めたものとして受け入れる。
- 明らかに今の状態や問題を書いているもの、または悩みと関係がないと思われるものだけ問い返す(6.6を参照)。


| 区分  | 人物  | 入力                     | ラベル                     |
| --- | --- | ---------------------- | ----------------------- |
| OK  | P01 | 年収は今より下げない             | ok                      |
| OK  | P02 | 子どもが小学校を卒業するまでは今の市内に住む | ok                      |
| NG  | P01 | 仕事にやりがいを感じない           | wrong_category(現状または問題) |
| NG  | P01 | 進め方を任される仕事がない          | wrong_category(原因)      |


**問い返し例**

- 「これは、今回は変えないと決めた条件ですか？それとも、今の状態を表していますか？」



### 4.3 現状

**定義**: 理想と同じ観点から見た、現在の状態

**役割**: 理想と比べることで、問題を定められるようにする。

**確認ポイント**

- 理想と同じ観点で書かれているか
- 理想と比べられる程度に具体的か
- 前提・制約や問題、原因が混ざっていないか
- 気持ちだけでなく、状況や事実(頻度、時間など)が含まれているか(含まれていなくても受け入れるが、含まれていれば良い点として伝えられる)


| 区分  | 人物  | 入力                                       | ラベル                             |
| --- | --- | ---------------------------------------- | ------------------------------- |
| OK  | P01 | 担当業務の多くは決まった検査手順の繰り返しで、自分で工夫できる場面がほとんどない | ok                              |
| OK  | P02 | 土日のどちらかと週3日の遅番があり、子どもと夕食をとれるのは週2日程度である   | ok                              |
| NG  | P01 | 給料が低い                                    | misaligned(理想は仕事での手応えについて書いている) |
| NG  | P02 | 子どもが小さい                                  | wrong_category(前提・制約)           |
| NG  | P01 | 手応えを感じられていない                             | wrong_category(問題)              |


**問い返し例**

- 「理想では仕事での手応えについて書いていますが、今の仕事では、工夫できる場面はどのくらいありますか？」
- 「この文は、今の状態と、理想との差のどちらを表していますか？」



### 4.4 問題

**定義**: 理想と現状の差

**役割**: 原因・課題・手段を考える起点になる。差を明確にしてから原因を考えることで、思いついた手段(転職など)から考え始めることを防ぐ。

**確認ポイント**

- 理想と現状の差として書かれているか
- 理想・現状の観点と対応しているか
- 原因、課題、手段が書かれていないか(重点項目)
- 特定の手段(転職など)を前提にしていないか


| 区分  | 人物  | 入力                                     | ラベル                                |
| --- | --- | -------------------------------------- | ---------------------------------- |
| OK  | P01 | 仕事の中で工夫して成果を出す場面がなく、手応えを感じられていない       | ok                                 |
| OK  | P02 | 子どもと過ごせる時間が、理想とする平日の夕方と週末の時間に対して足りていない | ok                                 |
| NG  | P01 | 仕事の手応えを増やす                             | wrong_category(課題)                 |
| NG  | P03 | デザインのスキルが足りない                          | wrong_category(原因)                 |
| NG  | P01 | 転職できていない                               | wrong_category(手段)                 |
| NG  | P01 | 決まった検査手順の繰り返しが多い                       | wrong_category(現状)                 |
| NG  | P01 | 給料が上がらない                               | misaligned(理想・現状は仕事での手応えについて書いている) |


**問い返し例**

- 「手応えに注目できていますね。この文は、理想と現状のどの差を表していますか？」
- 「転職できていないことで、理想とどんな差が生まれていますか？」



### 4.5 原因

**定義**: 問題(理想と現状の差)を生み出している要素

**役割**: 問題が起きている理由を整理し、取り組むべき課題を考える材料にする。

**確認ポイント**

- 問題とのつながりが読み取れるか
- 問題や現状の言い換えになっていないか
- 課題や手段が書かれていないか
- 変えられない前提を原因として書いていないか
- 気持ちだけが書かれていないか

**判定の注意**

- 確認できていない仮説でも受け入れる。仮説かどうかは問い返さない(6.7を参照)。
- 気持ち(「やる気が出ない」「自信がない」など)だけが書かれている場合は `ambiguous` とし、その気持ちを生んでいる状況を問う。気持ちを否定しない。
- 状況と気持ちが一緒に書かれている場合(「任される仕事がなく、やる気が出ない」など)は受け入れる。


| 区分  | 人物  | 入力                                | ラベル                   |
| --- | --- | --------------------------------- | --------------------- |
| OK  | P01 | 検査の手順が細かく決められていて、進め方を任される仕事がない    | ok                    |
| OK  | P02 | 店舗の営業時間に合わせたシフト勤務で、土日と夜の勤務が避けられない | ok                    |
| NG  | P01 | やりがいを感じないから                       | misaligned(問題の言い換え)   |
| NG  | P01 | やる気が出ない                           | ambiguous(気持ちだけ)      |
| NG  | P01 | もっと裁量のある仕事をする必要がある                | wrong_category(課題)    |
| NG  | P02 | 子どもがいるから                          | wrong_category(前提・制約) |


**問い返し例**

- 「この状況があると、なぜ手応えを感じにくくなるのでしょうか？」
- 「やる気が出ないと感じるのは、仕事のどんな場面ですか？」



### 4.6 課題

**定義**: 問題を解くために取り組むべき方向性

**役割**: 原因を踏まえて、何に取り組むかを定める。方向性を先に定めることで、最初に思いついた手段(転職など)に固定されることを防ぐ。

**確認ポイント**

- 原因とのつながりが読み取れるか
- 問題や原因の言い換えになっていないか(重点項目)
- 特定の手段(転職など)に限定されていないか
- 前提・制約と両立するか


| 区分  | 人物  | 入力                      | ラベル                           |
| --- | --- | ----------------------- | ----------------------------- |
| OK  | P01 | 自分の工夫が成果に反映される仕事の範囲を広げる | ok                            |
| OK  | P02 | 土日と夜の勤務が少ない働き方に切り替える    | ok                            |
| NG  | P01 | 手応えを感じられていない            | wrong_category(問題)            |
| NG  | P01 | 進め方を任される仕事がない           | wrong_category(原因)            |
| NG  | P02 | 土日休みの会社に転職する            | wrong_category(手段)            |
| NG  | P03 | デザインスクールに通う             | wrong_category(手段)            |
| NG  | P01 | 年収が下がっても、裁量のある会社に移る     | conflicts_premise(年収は今より下げない) |
| NG  | P01 | 手応えを感じられるようにする     | misaligned(問題を裏返しただけで、原因とのつながりが読み取れない) |


**問い返し例**

- 「この取り組みは、どの原因に対応していますか？」
- 「転職することで実現したいことは何ですか？それを課題として考えてみると、ほかの方法も見えてきそうです」
- 「この取り組みは、前提・制約として決めた条件と両立しそうですか？」



### 4.7 手段

**定義**: 課題に取り組むための具体的な行動

**役割**: 課題を、実行を検討できる行動に落とし込む。

**確認ポイント**

- 課題とのつながりが読み取れるか
- 「何をするか」が読み取れる程度に具体的か
- 前提・制約と両立するか
- 理想につながっているか

**判定の注意**

- 転職は、手段として受け入れる。転職するかどうかの良し悪しは判定しない。
- 実行が決まっていない候補でも受け入れる。
- 実行できるかどうか(求人があるか、採用されるかなど)の詳細は問わない。


| 区分  | 人物  | 入力                                      | ラベル                              |
| --- | --- | --------------------------------------- | -------------------------------- |
| OK  | P01 | 検査手順の見直しを任せてもらえるよう、上司に相談する              | ok                               |
| OK  | P02 | 本部(日勤・土日休み)への異動を希望し、並行して、同じ条件の市内の求人を調べる | ok                               |
| NG  | P01 | 仕事を頑張る                                  | ambiguous                        |
| NG  | P01 | 自分の工夫が成果に反映される仕事の範囲を広げる                 | wrong_category(課題)               |
| NG  | P03 | 仕事を辞めて学習に専念する                           | conflicts_premise(準備の間は今の仕事を続ける) |
| NG  | P01 | 資格を取る                                   | misaligned(課題とのつながりが読み取れない)      |


**問い返し例**

- 「この方法は、設定した課題のどの部分に取り組むものですか？」
- 「『頑張る』とは、具体的に何をすることですか？」

## 5. 判定ラベル



### 5.1 ラベル一覧


| ラベル               | 意味                                              | 追加情報                       |
| ----------------- | ----------------------------------------------- | -------------------------- |
| ok                | そのステップの役割を果たしている                                | なし                         |
| wrong_category    | 別のステップの内容が書かれている                                | どのステップの内容に見えるか(looks_like) |
| misaligned        | 前のステップとの対応やつながりが読み取れない(観点のずれ、因果のつながりが弱い、言い換えなど) | どのステップと対応していないか(against)   |
| conflicts_premise | 前提・制約と両立しない                                     | どの前提・制約と両立しないか(against)    |
| ambiguous         | 意味が複数に解釈でき、次のステップを考えられない(気持ちだけの原因を含む)           | なし                         |
| safety_concern    | 深刻な内容が含まれている(2.5)                               | なし                         |




### 5.2 複数該当する場合の優先順位

問い返しは1つだけにするため、複数のラベルに該当する場合は、次の順で1つを選ぶ。

1. safety_concern
2. wrong_category(特に問題と課題の混同、手段の入り込み)
3. misaligned
4. conflicts_premise
5. ambiguous

**理由**: 安全への対応を最優先にする。次に、項目を取り違えたまま先に進むと後のすべてのステップに影響するため、取り違えを優先する。

### 5.3 AIの出力形式

AIの判定結果は、次の形式(JSON)で返す。形式が正しくない出力は表示しない。

```json
{
  "step": "ideal",
  "label": "wrong_category",
  "looks_like": "means",
  "against": null,
  "evidence": "転職したい",
  "good_point": "",
  "question": "転職した先で、どんな状態になっていたいですか？"
}
```


| 項目         | 内容                                                                   |
| ---------- | -------------------------------------------------------------------- |
| step       | 判定したステップ(ideal / premise / current / problem / cause / task / means) |
| label      | 判定ラベル                                                                |
| looks_like | wrong_category のとき、どのステップの内容に見えるか                                    |
| against    | misaligned または conflicts_premise のとき、対応していないステップや条件                  |
| evidence   | 判定の根拠となった、ユーザーの入力の一部                                                 |
| good_point | 良い点。なければ空                                                            |
| question   | 問い。label が ok または safety_concern のときは空                               |

## 6. 設計判断



### 6.1 理想を最初にする

不満や手段(転職など)から考え始めると、何を変えたいのかを整理しないまま手段を決めてしまう可能性がある(設計思想 1章)。目指す状態を先に決めることで、比べる基準を作る。

### 6.2 前提・制約を現状の前に置く

変えられない、または変えたくない条件を先に切り分けておくことで、現状や問題に、変えられないことが入り込むのを防ぐ。

### 6.3 原因を独立させる

問題から課題へ直接進むと、問題を裏返しただけの課題(「手応えを感じられていない」→「手応えを感じられるようにする」)になりやすい。原因を独立させることで、課題を原因から導けるようにする。

### 6.4 課題と手段を分ける

課題を「具体的な取組」とすると、最初に思いついた手段が課題として固定されやすい。課題を「取り組む方向性」、手段を「具体的な行動」と分け、方向性を先に定めることで、手段の選択肢を広げてから選べるようにする。

### 6.5 転職を手段として扱う

転職は、課題に取り組むための手段の一つである。理想・問題・課題に書かれた場合は問い返すが、手段に書かれた場合は受け入れ、良し悪しは判定しない。アプリの目的は転職を勧めることでも止めることでもなく、何を変えたいのかを整理することにあるため。

### 6.6 前提・制約をすべて確認しない

前提・制約は、入力した時点で後の思考の範囲を狭めるため、本来はすべて確認したい。しかし、すべてに問い返すと負担が大きくなる。そのため、明らかに今の状態や問題を書いているもの、または悩みと関係がないと思われるものだけを確認する。

### 6.7 原因の仮説を問わない

原因の裏付けは重要だが、このアプリの目的は「原因を考えて課題につなげること」にある。仮説かどうかまで問うと焦点がずれるため、MVPでは問わない。

### 6.8 気持ちだけの原因は、状況を問う

転職の悩みでは、原因に気持ち(「やる気が出ない」など)が書かれやすいと考えられる(設計思想 仮説3)。気持ちそのものは否定せず、その気持ちを生んでいる状況を問うことで、課題につながる原因を考えられるようにする。

### 6.9 抽象的な入力を誤りとしない

理想や課題は、ある程度抽象的であることが自然である。抽象度の高さそのものではなく、「次のステップを考えられるか」で判定する。

### 6.10 深刻な内容には、AIの問いではなく固定の文で対応する

深刻な内容に対して、AIが毎回文を生成すると、不正確な案内や不適切な言葉づかいになるおそれがある。そのため、AIは検知だけを行い、案内はあらかじめ用意した固定の文で行う。

## 7. AIの限界と対策


| 限界                          | 対策                                                          |
| --------------------------- | ----------------------------------------------------------- |
| 誤った判定をすることがある               | 指摘は仮説として示し、ユーザーは「このまま進む」を選べる                                |
| 判定の根拠が分かりにくい                | 根拠となった入力の一部(evidence)を必ず示す                                  |
| 指示に反して答えや候補、キャリアの助言を出すことがある | 出力形式を固定し、問いに答え・候補・助言が含まれていないかテストで確認する                       |
| 同じ入力でも判定がばらつくことがある          | 出力のランダムさを下げる設定にし、モデルのバージョンを固定する                             |
| ユーザーの入力に含まれる指示に従ってしまうことがある  | ユーザーの入力とAIへの指示を区切り、入力内の指示に従わないよう指示する。テストデータで確認する            |
| 過剰に指摘することがある                | 迷う場合は問い返さないルールにし、過剰指摘率を評価する                                 |
| 深刻な内容を見逃すことがある              | 迷う場合は safety_concern とする。あわせて、相談先への案内を画面に常に表示することを要件定義で検討する |
| 判定が苦手な組み合わせがある              | 評価で、ラベルごとの正答率を測り、苦手な判定を明らかにして記録する                           |
